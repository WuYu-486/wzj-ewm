# 01. 优化工作

> 本文档只做问题分析与方案设计，不含任何功能性代码改动。
> 编写时间：2026-09-14
> 对应代码：`weiClass-master/`（当前运行入口为 `web.py`）

---

## 背景

当前项目已可正常运行：Flask 服务跑在 `0.0.0.0:5000`，管道会持续轮询微助教接口，捕获到二维码签到后把二维码 URL 跟随重定向，前端页面拿到结果后自动跳转，在微信内置浏览器里完成签到。

实测可用，但暴露出两个影响日常使用的问题，本文档分别记录。

---

## 问题一：签到成功后不会停止，会重复跳转到已结束的签到页

### 现象

- 只要捕获过一次签到，之后就一直往那个签到的页面跳。
- 老师发了新的签到，页面也还是跳旧的。
- 刷新页面、重新打开页面，立刻又弹回那个旧的签到页，没法重新开始监听。

### 实测复现（2026-09-14 19:37，日志实录）

一次真实的签到过程，完整暴露了这个问题的全部环节：

| 时间 | 日志 | 说明 |
| --- | --- | --- |
| 19:37:14 | 获取到二维码URL → 最终重定向URL | 捕获第 1 个二维码，`success` 置 1 |
| 19:37:14 ~ 19:37:54 | 每 10 秒重复一次"获取到二维码URL + 最终重定向URL" | 持续捕获，每轮的重定向 `extra` 参数都**不同** |
| 19:37:25 | `qr_url为空，前方拥挤` | 对应 `type == 3` |
| 19:38:00 | `检测到关闭信息` → 优雅关闭 WebSocket 客户端 | 对应 `type == 2`，老师结束了签到 |
| 19:38:01 | `至少有一个任务成功完成` → `开始关闭管道...` → `管道关闭完成` | **整个管道被关闭** |
| 19:48 | `/health` 返回 `{"pipeline_running": false, "success": 1}` | 管道已死，`success` 仍停在 1 |

从这份日志能得到三个额外结论，比预想的更严重：

1. **管道关闭后不会自行恢复。** `pipeline_running` 变成 `false` 之后，进程还在、页面还能开，但**再也不会捕获任何新签到**了。必须重启服务才能重新开始监听 —— 而此刻 `success` 仍是 1，页面还会一直往那个早就关闭的旧签到跳。等于说一次签到就把整个服务"用完即废"了。
2. **一次捕获会跑两遍处理逻辑。** 日志里每轮都出现**两行**时间戳完全相同的"获取到二维码URL"。原因是 `Pipeline.callback()` 里同时做了两件事：一是把 URL 塞进 `result_queue`，二是 `run_coroutine_threadsafe` 直接调用 `_process_callback_result()`；而 `get_status()` 又会从 `result_queue` 里取出同一个 URL **再跑一遍**。同一个二维码被重复处理，纯属浪费，也让日志难以判读。
3. **二维码有效期极短，约 10 秒一换。** 每轮重定向 URL 里的 `extra` 参数每次都不同，说明每个二维码都是独立一次性凭证。这意味着"捕获 → 前端 500ms 轮询 → 用户浏览器跳转"这条链路上，等真正跳过去时，二维码**很可能已经过期**了 —— 这正是需求里提到的"二维码过期、二维码失效"报错的来源。

### 现状代码分析（根因）

定位到 7 处相互叠加的原因：

**原因 1：`success` 标记一旦置 1 就永远不复位**

`web.py` 的 `Pipeline._process_callback_result()` 拿到重定向地址后执行：

- `self.result = str(final_url)`
- `self.success = 1`

此后全项目没有任何一处把 `success` 改回 `0`，也没有任何一处清空 `self.result`。
于是 `/qr_code` 这个接口从那一刻起**永远**返回 `success: 1` 加同一个旧 URL。

**原因 2：前端只要看到 `success === 1` 就无条件跳转**

`templates/index.html` 的 `checkQRCodeStatus()` 里：

```js
if (data.success === 1) {
    window.location.href = data.qr_url;
}
```

前端没有任何"这一轮我已经跳过了"的记录，所以只要页面还在，每 500ms 就会重新触发一次跳转；用户手动返回页面，也会立刻被再次弹走。

**原因 3：本应"取到二维码就关闭"的开关是死代码**

`web.py` 在创建 WebSocket 客户端时写了：

```python
client.webT = True  # 获取到二维码后自动关闭
```

但 `getSocket.py` 全文**从未读取过 `webT`**，这个属性没有任何作用。
也就是说，作者原本想要的"拿到一次二维码就收工"从未实现，客户端拿到二维码后会一直挂着。

**原因 4：拿到二维码后不终止，服务端一推就再触发**

`getSocket.py` 的 `_handle_qr_message()` 中，二维码类型 `type == 1` 时只调用 `self.qr_callback(qr_code_url)`，调用完不结束、不退订，所以服务端后续再推消息就会一遍遍触发回调、一遍遍覆盖 `self.result`。

**原因 5：完全没有"签到是否成功"的判断环节**

`_process_callback_result()` 的逻辑是：请求二维码 URL、跟随重定向、把 `resp.url` 当作最终地址，然后直接认定成功。
它只证明"这个二维码链接能跳转"，不能证明"我真的签到成功了"。
二维码过期、二维码已失效、老师已结束签到等情况下，同样会走到 `success = 1`，前端照样跳，跳过去只能看到一个报错页面 —— 但程序自己感知不到。

**原因 6：任务"成功完成"后直接把整条管道关掉，且无法恢复**

`web.py` 的 `process_signatures()` 用 `asyncio.wait(..., return_when=FIRST_COMPLETED)` 等任务，只要有一个任务结束（例如收到 `type == 2` 的关闭信息），就取消其余任务并返回；随后 `_main_async()` 的 `finally` 分支执行 `await self.shutdown()`，**整条管道就此终结**。
而管道对象的 `is_running` 一旦变成 `False`，没有任何机制能把它重新拉起来。前端只能眼睁睁看着 `pipeline_running: false`，除了重启进程别无他法。

**原因 7：同一个二维码被重复处理两遍**

`Pipeline.callback()` 既把 URL 放进 `result_queue`，又通过 `run_coroutine_threadsafe` 直接调用 `_process_callback_result()`；而 `get_status()` 会再从 `result_queue` 里把同一个 URL 取出来跑一遍 `_process_callback_result()`。结果是每个二维码都要请求两次、跟随重定向两次，日志里成对出现。

### 影响

- **一次签到即报废**：管道在签到结束后自动关闭且不可恢复，之后的所有签到都捕获不到，必须重启服务。这是最严重的一条。
- 错过后续签到：一次成功的记录把管道"焊死"在旧签到上，新的签到捕获到了也没意义。
- 页面不可用：无法停留在监听界面，刷新即被弹走，等于每次都要重新部署。
- 无法区分真假成功，二维码失效时会误判为成功。
- 二维码约 10 秒即过期，捕获到跳转之间天然存在延迟，实际跳转成功率受链路耗时影响。
- 重复处理同一个二维码，无谓地多打一倍请求。

### 期望行为（按需求原文整理）

1. 捕获一次签到之后，**继续监听**，继续处理后续的签到。
2. 如果能**确认到签到成功**，这一轮才停下。
3. 如果**无法确认**（二维码过期、二维码失效等报错），就继续捕获签到，不要误判成功。
4. 退一步说，**如果始终无法确认签到状态，那就一直重复签到也没关系**。

也就是说：宁可多签，不可漏签；宁可重复跳转，不可误判成功。

### 待确认的技术问题

这几项需要实际抓包/试错才能确定，是方案落地的前置条件：

1. **微助教有没有"查询我的签到结果"的接口？**
   如果有，`success` 应该由这个接口的返回值决定，而不是由"重定向是否成功"决定。这是本问题最理想的解法。
2. **跟随重定向拿到的最终 URL，语义到底是什么？**
   是签到提交接口、还是签到结果页、还是失败提示页？需要分别抓取"二维码有效"和"二维码失效"两种情况对比返回内容。
3. **二维码失效 / 过期时，服务端推送或跳转返回的特征是什么？**
   `getSocket.py` 目前已知处理了 `type == 1`（正常二维码）、`type == 2`（检测到关闭信息）、`type == 3`（qr_url 为空、前方拥挤），但"已过期/已失效"属于哪一种尚未确认。
4. **既然二维码约 10 秒一换，跳转策略要不要跟着改？**
   现在前端是每 500ms 拉一次 `/qr_code`，拿到就走。从捕获到浏览器真正完成跳转，耗时可能已经超过二维码的有效期。需要考虑：是让后端**主动把最新二维码推给前端**（而不是等前端轮询），还是前端拿到后立刻跳、失败再回来拿新的。这个决策会直接影响"跳过去看到失效页"的概率。
5. **一个时间段内是否可能存在多个并行签到？**
   当前代码是按 `isQR` 逐个建 WebSocket 客户端、并行处理的，需要确认是否符合预期。

### 建议方案方向（未实施）

思路是给管道加上"轮次""确认""自愈"三个概念：

- **管道自愈（最高优先级）**：签到结束、WebSocket 断开、管道被关闭之后，必须能够**自动重建**并回到监听状态，而不是让 `is_running` 永远停在 `False`。这是"一次签到即报废"的直接解法，也是保证后续签到不漏的前提。
- **加轮次（round）**：每捕获到一个新的二维码算作新一轮，记录轮次编号、二维码 URL、捕获时间、处理结果。前端能区分"这是新的一轮"还是"上一轮的残留"。
- **成功后复位而不是永久置位**：一轮处理完成后，`success` 需要有明确的复位时机（例如本轮确认结束后、或进入下一轮时自动清空），让 `/qr_code` 能回到"等待"状态。
- **同一二维码去重**：`callback()` 与 `get_status()` 的双重处理路径需要收敛成一条，避免同一轮被处理两次。
- **前端增加"已跳转过"的记忆**：跳转前先在页面侧记录"第 N 轮已跳转"，返回页面时不再因为同一条旧记录反复跳走，而是回到监听态并展示历史轮次。
- **增加结果确认环节**：跳转后（或跳过之后）调用签到结果接口核对，只有核对到"已签到"才把该轮标记为最终成功并停止这一轮；核对失败或接口报错则保留监听、继续捕获。
- **兜底策略**：确认环节本身失败时，按需求第 4 条处理 —— 不做悲观判定，继续监听、继续签，绝不能因为"确认不了"就当成"签好了"而停下。
- **清理死代码**：确认 `webT` 的取舍 —— 要么真正实现"取到即关闭"，要么删除，避免误导后来人。

### 验收标准

- [ ] **老师结束签到后，`pipeline_running` 能自动回到 `true`，无需重启进程。**（对应"一次签到即报废"）
- [ ] 一次签到结束后，`/qr_code` 的 `success` 能复位，不再永久返回旧 URL。
- [ ] 完成一次签到后，页面回到监听状态，能够继续捕获并处理下一次签到。
- [ ] 二维码失效/过期时，程序**不会**误报成功。
- [ ] 确认不到签到结果时，行为是"继续监听继续签"，而不是"停止"。
- [ ] 刷新页面不会自动弹回旧的签到页。
- [ ] 同一个二维码不会被重复处理两次。
- [ ] 页面上能看到本轮与历史轮次的处理情况。

## 问题二：openid 只能改文件，更换不方便

### 现象

每次 openid 过期（约两小时一次），都要：

1. 打开 `config.ini`；
2. 手动把新的 openid 字符串替换进去；
3. 回到命令行把服务**整个重启**。

一天下来要重复很多次，而且改文件、重启都需要接触服务器，人不在电脑前就完全没法处理。

### 现状代码分析（根因）

- `settings.py` 在 import 时读取 `config.ini`，把 openid 塞进环境变量 `os.environ["OPENID"]`。
- `web.py` 在**模块顶层**执行 `openid = os.getenv("OPENID")`，也就是说 openid 在进程启动、模块被导入的那一刻就被固定下来了。
- `create_pipeline()` 用的是这个顶层变量，且只在 `__main__` 里被调用一次。

三者叠加的结果：openid 与"进程生命周期"绑定死了，除了改文件加重启，没有任何运行时更换的途径。

### 期望行为（按需求原文整理）

1. **自动从链接中捕获 openid**：不需要人肉从网址里抠那串字符。
2. **在前端页面上显示当前 openid**，随时能看到现在用的是哪一个。
3. **openid 失效了直接换就行**：在页面上直接替换，立即生效，不用改文件、不用重启。

### 建议方案方向（未实施）

- **提取规则**：用户粘贴的链接形如
  `https://v18.teachermate.cn/wechat-pro-ssr/?openid=<32位字符串>&from=wzj`
  从查询参数里取 `openid` 的值即可；同时应兼容"只粘贴裸 openid 字符串"的情况。
  （出于安全考虑，本文档不记录真实的 openid 值。）
- **新增接口**：
  - 一个提交接口，接收整条链接或裸 openid，完成提取、校验、生效。
  - 一个查询接口，返回当前正在使用的 openid（**脱敏显示**）。
- **热替换**：提交后需要以新 openid 重建数据管道 —— 关掉旧管道（含其 WebSocket 连接）→ 用新凭据建新管道，全程不重启进程。要特别处理"旧管道正在处理签到"时的切换时序，避免新签到被旧连接吞掉。
- **前端配置区**：页面上加一块"当前 openid + 更换输入框 + 提交按钮"，并显示更换结果（成功/失败原因）。openid 失效时页面上最好有显式提示，而不是让用户对着 `success: 0` 干等。
- **是否落盘**：可以选择把新 openid 同步写回 `config.ini`，这样进程重启后不用重新粘贴；也可以选择不落盘，只在内存中生效。建议落盘，并在文档里说清楚。

### 安全提示（重要）

- **openid 等同登录凭证**，拿到它就能以该学生身份操作。前端显示时必须脱敏（例如只露首尾各 4 位），不要原样打在页面上。
- 当前服务监听 `0.0.0.0:5000`，**同一局域网内任何人都能访问**。如果加上"提交 openid"的接口，等于把这个能力开放给了整个局域网。落地时需要考虑：
  - 是否把监听地址收回 `127.0.0.1`；
  - 或者给配置接口加一层简单的口令/Token 校验；
  - 或者明确接受这个风险（仅校园网、临时使用）。
- `config.ini` 里存有 openid，属于敏感信息，**不要提交到 Git**。

### 验收标准

- [ ] 在页面上粘贴整条含 openid 的链接，提交后新 openid 立即生效，无需改文件、无需重启。
- [ ] 页面上能随时看到当前使用的 openid（脱敏）。
- [ ] 能兼容"只粘贴裸 openid"的输入。
- [ ] openid 失效时页面有明确提示。
- [ ] 局域网可访问性 / 凭证展示带来的风险已在文档或界面上明确告知。

## 建议实施顺序

1. **先做问题二**：改动面小、收益直接，能立刻省掉"改文件 + 重启"的操作成本，也为问题一的调试提供便利（调试期间 openid 会频繁失效）。
2. **再做问题一**：需要先抓包确认"签到成功"的判定依据，方案依赖调研结果，工作量与不确定性都更大。
3. **两项都落地后**：更新 `Agent.md` 里已过时的启动说明与限制说明。
